# Architecture

A single-page React app, prerendered to static HTML per page at build time. No backend: content is TypeScript data in the repo.

## Layers

```
src/app        shell: App, routing/, seo/, analytics/, hydration/, prerender entry
   │  imports features only through their index.ts
   ▼
src/features   work · about · contact · cv · case-studies · image-viewer · privacy · accessibility
   │  never import each other
   ▼
src/shared     ui · layout · media · hooks · lib · content
                 never imports app or features
```

- A **feature** (vertical slice) owns its view, components, hooks, copy (`*.content.ts`), types (`*.types.ts`) and tests. Its `index.ts` is the public API that `src/app` imports.
- **Shared** code is what two or more slices use: UI primitives, the header and footer, image components, hooks, route helpers, profile data.
- The rules are enforced by ESLint (`no-restricted-imports` per layer, as regular expressions), not only by convention. A slice may import its own files across folders (`#features/about/about.content.ts`), never another slice.
- Imports use subpath aliases from `package.json` ("imports"): `#app/*`, `#features/*`, `#shared/*`, `#test/*`. TypeScript, Vite, Vitest and Node all read the same mapping. Within a folder or below it, imports are relative (`./x.ts`, `./AboutView/AboutView.tsx`); going up or across uses the alias, never `../`.

## Files and folders

One role per file, and one folder per component or domain, so no file grows long (ESLint `max-lines`: 200 lines of code, tests and copy excepted).

```
src/shared/ui/Button/         a component folder
  Button.tsx                  structure and behaviour only
  Button.types.ts             its props and other types
  Button.styles.ts            every Tailwind class it uses (a `styles` object)
  Button.test.tsx             its tests
src/shared/lib/routes/        a domain folder
  routes.constants.ts  routes.types.ts  routes.utils.ts  routes.test.ts
src/features/about/
  index.ts                    the slice's public API
  about.content.ts  about.types.ts
  AboutView/                  the view (a component folder)
  components/FaqItem/ ...     the slice's own components
```

- Components: `PascalCase/PascalCase.tsx`, one component per file. Hooks: `useX.ts` next to what uses them, or in the slice's `hooks/`. Other modules: kebab-case with a role suffix: `*.types.ts`, `*.styles.ts`, `*.constants.ts`, `*.utils.ts`, `*.content.ts`, `*.context.ts`. Inside a component folder they take the component's name (`CaseNavLink.constants.ts`, `Dialog.utils.ts`).
- Classes: a `*.styles.ts` exports `styles`, one key per styled element; state-dependent classes are functions (`styles.pill(active)`). Values are composed with [`clsx`](https://github.com/lukeed/clsx); variant sets use [`cva`](https://cva.style) (`button({ variant })`) with the variant names from Figma. Prettier sorts classes inside both. ESLint rejects class strings written into `className` in a component. There is no `tailwind-merge`: it reads the token type styles as colours and drops them.
- Shared class lists (`FOCUS_RING`, `TEXT_LINK`, `BUTTON_HEIGHT`, `BULLET_LIST`) live in `src/shared/lib/ui/ui.styles.ts`; `EXTERNAL_LINK` (target and rel of a new-tab link) in `ui.constants.ts`.
- A row of text links that can wrap (the Behind the Design banner) is spaced like a row of buttons: each link gets `BUTTON_HEIGHT` (a bordered Button's height) and the row `gap-y-sm`, the gap between buttons.

### Storybook

Every shared component (`shared/ui`, `shared/layout`, `shared/media`) and the consent box have a story next to them (`Button/Button.stories.tsx`), with the variants from Figma, real copy and a light/dark toolbar. `yarn storybook` opens it locally on port 6006.

- Welcome page: `.storybook/Welcome.mdx` opens first. It says what the library is, how it comes from the Figma design system, what each sidebar group holds and how to use the toolbar and the Accessibility panel. It sits outside `src` so Tailwind does not scan its prose for class names. The sidebar order is set in `preview.tsx` (`storySort`): Welcome, Foundations, UI, Layout, Media, Patterns.
- Tests: `src/test/stories.test.tsx` runs every story in Vitest with the Storybook settings (`composeStories`): it renders, runs the story's `play` checks (clicks, `aria-expanded`, callbacks), then axe for WCAG 2.2 A/AA. It also fails when a component folder has no story. Colour contrast and page-level rules stay with `yarn a11y`, which sees real layout.
- Published: Netlify's production build (main) runs `yarn build-storybook` into `dist/storybook`, served at `/storybook/`. It is a separate build, so the site's pages never load its code; `X-Robots-Tag: noindex, nofollow` (`public/_headers`) and a robots meta keep it out of search. The Work page links it from the Behind the Design banner ("Explore the Storybook Library"), with `PROFILE.storybookUrl`: an absolute URL in builds, because only production builds Storybook; on `yarn dev` it points to the local `yarn storybook` (port 6006), so unreleased stories show there.
- Deploys: every build renames the story files and Netlify removes the old ones, so a Storybook tab opened before a deploy would fail with "Failed to fetch dynamically imported module". `.storybook/preview-head.html` reloads the preview once on `vite:preloadError` (at most once in 10 s). The site itself is one bundle with no lazy chunks, so it does not have this problem.
- Static files: only `public/assets/cases/project-planning` is copied (the screenshots the media stories show), not the site's `public/` with its headers and sitemap.

## Routing

- `src/shared/lib/routes/` is the single source: `VIEW` (ids), `VIEW_PATHS` (URLs), `SECTION` (anchors other pages or shared links point to), titles and nav items. They are `as const` objects with derived union types, so a wrong id is a type error.
- `src/app/routing/useHistoryRoute.ts` keeps the view in browser history: one entry per view change, scroll position restored on Back and Forward. Positions are kept in memory by entry id (`kbId`) and written into the history only when leaving a page (a navigation, `pagehide`), never while scrolling: in-app browsers (Messenger, Instagram, LinkedIn) flash their loading bar on every history write. A new view remounts and fades in, starting at its top (or section) at once; a jump within the same view (Explore Case Studies) only scrolls, smoothly unless the visitor asks for reduced motion ([motion.md](motion.md#smooth-scrolling)). On first load it normalises the URL: old hash links (`/#about`, used before 3.0.0), aliases (`/resume`, the CV's old name, opens `/cv`) and the file forms Netlify also serves every page under (`/about.html`, `/about/index.html`) become their path; unknown paths become `/`. A link to a section of the page already open that the browser follows by itself (a plain `<a href="#career">`, a hash typed in the address bar, an in-app browser reusing the page) is a fragment navigation: the browser adds an entry the app never wrote, fires `popstate` and jumps to the `<section>`. The app takes that entry as a new section link, not as Back: it lands on the heading in the next frame, after the browser's jump (`afterBrowserJump`), and gives the entry its id and normalised address, one write as on the first load.
- A one-page build with a relative base (`vite build --base ./`, e.g. a claude.ai artifact) has no other paths to load, so `src/main.tsx` turns on hash routing: the path travels in the hash (`#/about`, `#/about#career`). The site itself always uses real paths.
- The URL hash is a **section anchor** (`/about#career`). `Section` (`src/shared/ui/Section/Section.tsx`) gives every section heading a `HeadingAnchor` link that copies the section's address with the link tag `?ref=section-link` (`sharedSectionUrl`: the page's own path, the tags and the anchor). A copier who came from a tagged link passes its tag on with `utm_medium=section-link` instead (`/about?ref=acme&utm_medium=section-link#career`), so the visit still counts for that company or channel; click ids never travel (`sectionLinkQuery`, [analytics.md](analytics.md#tagged-links)); a titled `Callout` with an `id` gets one too (the Work page's Behind the Design banner, `/#behind-the-design`). `src/app/routing/useSectionHash.ts` keeps the hash on the section (or linkable banner) in view while scrolling, with `replaceState` (no history entries). Not in in-app browsers (`inAppBrowser()` in `src/shared/lib/browser/`, by user agent), for the loading-bar reason above; `e2e/history.e2e.ts` checks both in three browsers.
- Opening a section link (`/about#career`) does not wait for the app. A small script in `index.html`, right after the prerendered page, puts the section's heading below the sticky header as soon as the HTML is in (it sets `--kb-header-h` itself), and keeps it there while the page settles: an in-app browser's keyboard, toolbar or sheet resizing the window (below 480px the header and the consent box sit in the page, above it they float), fonts, the consent box. Browsers jump to the hash once more when the HTML is parsed (Firefox) or when the app's script has run (Chromium), to the `<section>` rather than its heading; the script puts that right, or undoes it when the visitor has already scrolled, also while their fling is still running, in the frame before Chromium would paint the jump. Chromium and WebKit also take focus away at that jump: a visitor who has tabbed into the page meanwhile gets it back, unless they clicked since. It lets go at the visitor's first touch, wheel, key or click, at Back or Forward, or when the page scrolls away by itself (a screen reader, find in page). It marks `<html>` with `data-kb-anchor-held` (`ANCHOR_HELD_ATTRIBUTE`), and on the first load `useRouteFocus` then only moves focus to the heading, and only while nothing has focus (WCAG 2.4.3: a visitor who tabbed in before the app started keeps their place); without the section in the HTML (the dev server, a one-page build) the app scrolls to it once. The section is the hash up to the first `?` or `&` (`readRoute`), because some apps write their tracking tag after the hash (`#career?fbclid=...`). Tests: `src/app/routing/section-link-script.test.ts` runs the script in jsdom; `e2e/section-links.e2e.ts` opens section links in three browsers, with the app's script held back, and on an Android phone in Messenger's in-app browser (the `android` project in `playwright.config.ts`, tests tagged `@android`: touch, real flings).

## Rendering and SEO

1. `yarn build` runs `vite build` for the browser bundle.
2. `yarn prerender` builds `src/app/prerender.entry.tsx` for the server, then `scripts/prerender.ts` renders every page inside a jsdom window at that page's URL and writes `dist/<path>.html` and `dist/<path>/index.html`, `dist/404.html` (noindex) and `dist/llms.txt`. A page that lost one of the template's icon links (`<link rel="icon">`, `apple-touch-icon`) fails the build: search engines read each page's own head.
3. Each page gets its own title, description, canonical URL, link-preview tags and JSON-LD from `src/app/seo/seo.utils.ts` (`headFor`). `src/app/seo/static-head.utils.ts` writes them into the template, with functions as replacements, so a `$` in the copy stays text. Site-wide data (WebSite, Person) stays in `index.html`, whose own tags say what the Work page says (for builds without the prerender).
4. In the browser, `src/main.tsx` adopts the static HTML (`hydrateRoot`): React keeps the elements the page brought and attaches to them, so nothing is rebuilt or repainted, no image loads twice and the largest paint is recorded once. `#root` names the view its HTML shows (`data-prerendered-view`); where the address opens another view (an old hash link: `/#about` is served the Work HTML) and where the root is empty (the dev server, a one-page build), `createRoot` renders the page anew (`adoptsPrerenderedHtml` in `src/app/hydration/`). On navigation, `useDocumentHead` updates the title, the page's JSON-LD and the same head tags: both read one list, `HEAD_TAGS` in `seo.constants.ts` (description, canonical, `og:url`, `og:title`, `og:description`, `twitter:title`, `twitter:description`). The robots tag stays as loaded: Google advises against changing it with JavaScript.

The app's first render in the browser must match the prerendered HTML, or React warns and, on a text mismatch, renders the page again. The prerender and `src/main.tsx` render the same element (`<StrictMode><App /></StrictMode>`, images from `ASSET_BASE`). What only the browser knows comes through `useSyncExternalStore` with a server snapshot (the document theme, the statistics choice, an in-app browser, the scroll position) or waits for `useHydrating()` (`src/shared/hooks/hydration/`), which is true on the server and while hydrating: the consent box appears right after. The footer's year is the build's (`APP_BUILD_YEAR`, `vite.config.ts`). `src/app/hydration/hydration.test.tsx` hydrates every page in Light and Dark (running the theme script from `index.html`) and fails on any warning; `e2e/hydration.e2e.ts` checks in three browsers that the app keeps the page's `<main>`.

Images in the first HTML show as they arrive, without JavaScript (`shown` in `useImageStatus`): the About portrait and the Work thumbnails no longer wait transparent for the app, and nothing fades on the first screen. An image the app adds or changes later (after a navigation, a theme switch) stays hidden until it has loaded and fades in, unless the browser already has it. The pages are prerendered light, so on a dark page a thumbnail's Light file waits hidden (`light-page-only`, `utilities.css`) until the app shows its Dark file.

What the JSON-LD says, and what keeps it true to the page:

- Work, the home page, is a `CollectionPage` about Karolina; About and the CV are `ProfilePage`s (Google's ProfilePage guide counts a home page with much else on it as not one); the other pages are `WebPage`s.
- The breadcrumb names are the labels on the page's own breadcrumb (a case study's `shortTitle`, the names in `PAGE_NAMES`), and Work has none, as on the page (Google asks for at least two items). `src/app/seo/useDocumentHead.test.tsx` renders every page and compares them.
- Each case study is a `CreativeWork` named as its Work card, with the card's Light thumbnail as `image` and its period (`CASE_PERIODS` in `seo.content.ts`, from its Timeline or Duration line) as `temporalCoverage`.
- `llms.txt` and the sitemap list the case studies in the Work page order (`WORK_CASES`); `llms.txt` puts Privacy and Accessibility last, under `## Optional` (`LLMS_OPTIONAL`).

The prerendered pages are written with no stored theme, so their theme switch says Light. Before the first paint, the inline script in `index.html` applies the visitor's theme to `<html>` and presses the matching switch button (`[data-theme-option]`, found by a MutationObserver as the parser adds them); the switch's look follows `aria-pressed` in CSS, so it is right from the first frame and React's takeover moves nothing. `useTheme` reads the same stored or system theme on its first render, so the switch React hydrates matches the pressed button. Keep `data-theme-option` on the buttons.

Tests keep the pieces in step: every view needs a path, a description (at most 160 characters) and a sitemap entry.

Google Search Console verifies the site's owner with `public/googlecf978c6093e1d8a5.html` (the HTML file method). Google checks it again from time to time, so the file stays as issued: `src/app/seo/site-verification.test.ts` fails if it is removed or edited, and `_headers` marks it `noindex`. The sitemap (`/sitemap.xml`) is submitted there.

## The CV and its PDF

`/cv` (`src/features/cv/`) is Karolina's CV as a page, built from the Figma CV frames with the site's tokens: Light or Dark on screen, always light on paper. Its two-column layout comes from the `sheet:` variant (`utilities.css`): from md on screen, and always in print, where A4 is narrower than md. The page is the version for people and search engines: it follows the browser's text size and contrast settings, and `yarn a11y`, the plain-text test and the prerender loop cover it like any page.

The PDF is made from that page, not from Figma: `yarn cv-pdf` (`scripts/cv-pdf.ts`) builds the site into `node_modules/.tmp/cv-pdf`, opens `/cv` in Playwright's Chromium in the light theme and prints it to `public/karolina-kita-cv.pdf`: A4, in English (`/Lang (en)`, the recruitment consent included), tagged (headings, lists, links), with an outline from the headings, clickable links and a footer in CSS `@page` margin boxes. The portfolio link gets its `data-pdf-href` (`?utm_medium=cv-pdf`, for Umami's UTM report; a `ref` tag would replace the session's own) only in the PDF. The footer takes the Label/Small type style and text/secondary from the build. The script also writes `scripts/cv-pdf.lock.json` (hashes of the sheet's text and of its elements and classes, and the page count), and `src/app/seo/cv-pdf.test.tsx` fails when the page's text, markup or classes no longer match it, or when the PDF loses its tags, links, A4 size, title or page count. Token or `print.css` changes do not show in the hashes: run `yarn cv-pdf` by hand after one that reaches the CV. The PDF is committed (`.gitignore` excludes every other PDF) and served under a fixed name, revalidated on every visit, with a canonical link to `/cv` (`public/_headers`). Netlify never runs the script.

## Visitor statistics

Umami Cloud counts visits, opt-in only. Its script reads the screen size and language, so it needs consent under ePrivacy Art. 5(3) and Art. 399 of the Polish Prawo komunikacji elektronicznej, cookies or not. What is sent, why, and the naming rules for new events: [analytics.md](analytics.md) (the tracking plan).

- `src/shared/lib/analytics/statistics-consent.utils.ts` holds the choice (`kb-statistics` in localStorage, `STORED_CHOICE`: "on-3" or "off") and loads the script only after a yes. A yes is stored with a number: when the statistics start collecting something new, the number goes up and earlier yeses are asked again (a plain "on" is a yes from before 3.14.0, "on-2" one from before 4.1.0). A no stays a no. A choice made in another tab, or the site's data cleared, applies to the open tabs at once (their `storage` event): anything but a yes stops the statistics there, a yes starts them and counts the page each tab shows. With Do Not Track or Global Privacy Control on, nobody is asked and nothing loads. Only the live host counts (`UMAMI.host`); dev, local previews, Netlify's own addresses (`*.netlify.app`) and the artifact never load it.
- The privacy slice (`src/features/privacy/`) asks: the consent box at the bottom of every page until the visitor decides (two equal buttons, a link to Umami and to the details), and the switch on /privacy to change the choice later. On `yarn dev` the box shows on every load to check its design and loads nothing; automated browsers (`navigator.webdriver`) never get it. Google's renderer starts with empty storage, so it sees the box: `data-nosnippet` keeps its text out of the snippets under search results.
- `src/shared/lib/analytics/analytics.utils.ts` sends page views and events through `track()`, the only way to count something. It overrides the address, title and referrer on each call, because the tracker's own are wrong in a single-page app (once the address changes, its referrer names the page just left, the first page included), so every call on a page has its pageview's referrer; `payload.utils.ts` cleans addresses (no hash, only `ref` and UTM parameters) and `beforeSend` (`data-before-send`) applies the same to the tracker's own requests and cancels them once statistics are off. It also always cancels the tracker's own error reports (type `error`, full stack traces), and the script tag sets `data-errors="false"`: `js-error` is the only error data. Every call carries the site's version as Umami's tag (`data-tag`, from `package.json` through `vite.config.ts`), so the dashboard can compare releases.
- The first pageview sends session data (`session.utils.ts`, `umami.identify()` without an id): window width and height and pixel density in ranges, the theme and whether it was picked, the in-app browser (`shared/lib/browser`), the site's version (as in the tag, so the dashboard lists it among the session properties) and, when the page was opened from a tagged link, its tag (`ref`, so later visits in the same session stay under it). An address that matches no page is kept by `src/main.tsx` before the app replaces it with `/`, and goes out as `page-not-found` with the first pageview.
- The tracker's own speed report (`data-performance`: Core Web Vitals in Umami's Performance tab) needs it initialised, so only its pageviews are off (`data-auto-pageview="false"`). It takes every history write as a new page: a new view goes through `history.pushState`, while the section hash, same-view jumps and the first load's normalised address use `replaceAddress()` (`shared/lib/routes/address.utils.ts`), which passes its wrapper. The tracker sends one speed report per view, 10 s after the view starts or earlier when the tab is hidden or the view changes, so INP and CLS cover only those first 10 s.
- While statistics are on, these listeners add detail (removed when they go off):
  - `engagement.utils.ts` sends `time-on-page` when the visitor leaves a page, switches tabs or closes it: engaged time (`time` as a dashboard group, `seconds`), scroll depth (`scroll`, in quarters) and the furthest section reached (`section`). Time counts only while the tab is visible and the visitor was active in the last 30 s. Each stretch is its own event, so a page's seconds add up.
  - `clicks.utils.ts` sends `dead-click` for a click or tap on something that does nothing (an image, a heading, text, a card's empty space) with `element`, `area` (section id, hero or landmark) and `label` (alt text, image caption, heading or card title), once per burst of quick clicks; a burst of three or more also sends `rage-click`. Cards are found by `data-card` (`shared/ui/Card`, `ShowcaseRow`, `ComparisonBlock`, `NumberedCards`); a card without a heading marks its title with `data-card-title` (`CaseImpact`'s stat cards). A caption names the figure around it unless the figure is a card (a testimonial's caption names a person), and the empty space around a captioned screenshot counts as `image`. Controls, links, drags, text selection, clicks without a pointer and a click or tap on the image viewer's image once it shows (it zooms; `data-clickable`, in `INTERACTIVE`) do not count.
  - `clicks.utils.ts` also sends `text-copy` (where copied text was, never the text: a label the selection holds part of is skipped for the next one, or left out), `engagement.utils.ts` `page-print`, and `errors.utils.ts` `js-error` for errors in the site's own scripts (at most three a page).
  - `input.utils.ts` adds `input` (mouse, touch, pen or keyboard) to every event a click or key started, so the dashboard tells taps from clicks. `link-ref`, `time-on-page` and `page-not-found` have none.
- The privacy policy (`privacy.content.tsx`) lists what is counted; a new event needs a line there too, and a row in `docs/analytics.md` (`tracking-plan.test.ts` checks it). `e2e/analytics.e2e.ts` checks the whole flow in real browsers with the real tracker, and `e2e/analytics-links.e2e.ts` each kind of tagged link from landing to consent (the live-site setup and the request capture they share: `e2e/helpers/umami.utils.ts`).

## Images

- `public/assets/site/` (portrait, link-preview PNG `og-cover.png`: see [design.md](design.md#link-preview-image)) and `public/assets/cases/<case>/` (WebP screenshots, `thumbnail-light.webp` and `thumbnail-dark.webp`). Content refers to images by their path under `/assets`.
- `vite.config.ts` provides `virtual:asset-sizes`: the pixel size of every image, read from its PNG or WebP header at build time. Every `<img>` on the pages (`Screenshot`, `CaseThumbnail`, the portrait) takes it as `width` and `height` through `assetSize()` (`src/shared/media/asset-size/`), so the prerendered HTML already holds each image's height and the text below does not move when the file arrives; CSS keeps the images responsive (`w-full h-auto`, or a frame the image covers). `src/app/image-sizes.test.tsx` checks every image of every prerendered page. The image viewer uses the same sizes to reserve the right space before an image arrives.
- On hover, a case image zooms by 2% inside its clipped frame (`Screenshot`, `CaseThumbnail`), which hides about 1% of its width and height at each edge. Content stays outside that band on framed screenshots, and outside twice the band on images without a frame and on Work thumbnails (their own card or legend must stay whole). A file that is too tight gets padding in the image itself, its canvas extended evenly with its own background. `src/app/zoom-margins.test.ts` checks every case image (`src/test/image-margins.ts`).
- Images load lazily on the page. A case study's full screenshots load in the background when the visitor shows interest in it: the pointer over, or keyboard focus on, a link to the case (`src/app/App/usePreloadCaseImages.ts`), and on arrival for the open case (`useCaseGallery`). The image viewer still opens at once, and a visitor who only reads the Work page does not download every screenshot (about 6 MB per theme). Both load the files of the theme the page shows: the Dark ones in Dark mode. Loading goes through `src/shared/media/image-preload/image-preload.utils.ts`: a few at a time, nothing with Save-Data or on 2G.
- The image viewer opens on the page's own file. A screenshot can also have a sharper copy for close looks, the same file name in a `zoom/` folder beside it (`cases/<case>/zoom/<file>`, about twice the pixels): `useCaseGallery` passes it to the viewer as `zoomSrc`, and `useSharpImage` (`src/features/image-viewer/hooks/`) loads it only once the screen needs more pixels than the page's file has, on a dense screen, at the viewer's zoom or under a pinch-zoom, and never with Save-Data or on 2G. It takes over once decoded, sized by the page file's width, so nothing moves; the page and its preloads never download it. Not `srcset`: the browser picks a candidate by the screen's density, which a pinch-zoom does not change. `e2e/image-sharpness.e2e.ts` checks that nothing scales the viewer's image (no transform, filter or will-change), so a pinch draws it again from the file.
- Fonts are not preloaded. Checked on 2026-10-20: a `<link rel="preload" as="font">` with `crossorigin` makes WebKit download the font twice, and one without makes Chromium and Firefox do so; `e2e/loading.e2e.ts` checks that every font downloads once.
- No `srcset` on the lazy thumbnails. Checked on 2026-10-20: with a `srcset`, WebKit loads a `loading="lazy"` image eagerly, so the thumbnails competed with the first screen and held up the load event (`e2e/motion-a11y.e2e.ts` caught it). Smaller thumbnail files would need a single smaller `src` instead.

## Styling

Tailwind v4 with the defaults removed: only KitaBranding token utilities exist (`bg-bg-canvas`, `p-md`, `text-body-md`). Dark mode swaps CSS variables through the `dark` class on `<html>`; there are no `dark:` variants. See [design.md](design.md).

`src/styles/app.css` is the entry: it imports `tokens.css` (the token variables), `print.css`, `theme.css` (tokens → Tailwind theme, the named animations), `utilities.css` (named utilities and variants, the scroll reveal), `base.css`, `dialog.css` (modal backdrop), `lightbox.css` (image viewer) and `motion.css` (theme cross-fade, reduced-motion reset). Component classes live in each component's `*.styles.ts`. Motion, from the tokens to every animation on the site and its test: [motion.md](motion.md).

## Adding a page

1. Add the id to `VIEW`, its path to `VIEW_PATHS` and its title to `VIEW_TITLES` in `src/shared/lib/routes/routes.constants.ts`. The title is also the page's `og:title` and `twitter:title`; tests ask every title and description to be unique.
2. Create `src/features/<name>/` with the view folder (`<Name>View/`), `<name>.content.ts`, types, components and an `index.ts`.
3. Map the view in `src/app/App/App.constants.tsx` (`VIEW_RENDERERS`: a missing entry is a type error).
4. Add its description and its name in `src/app/seo/seo.content.ts` (`PAGE_DESCRIPTIONS`; `PAGE_NAMES`: the name its breadcrumb shows, or for a case study its Work card's title, and its period in `CASE_PERIODS`) and its URL in `public/sitemap.xml` (a case study in the Work page order). Its breadcrumb starts with `HOME_CRUMB`, or `WORK_CRUMB` if it is a case study. `llms.txt` lists it by itself: under About Karolina, or last if you add it to `LLMS_OPTIONAL` (`seo.constants.ts`).
5. `yarn verify`.
